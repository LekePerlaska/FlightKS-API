# FlightKS API

A production-ready **flight booking platform API** built with ASP.NET Core 10.0. Handles the full booking lifecycle — search, seat selection, booking, payment, ticketing, and real-time seat availability — with role-based access control for users, administrators, and flight managers.

## Getting Started

```bash
# Copy environment template
cp .env.example .env
# Edit .env with your credentials

# Build the API image
docker compose build api

# Start the full stack (API, Postgres, Keycloak, Redis, Loki, Grafana, Frontend)
docker compose up -d

# Start just the API and its dependencies
docker compose up -d api

# Tail API logs
docker compose logs -f api

# Stop everything (named volumes are preserved)
docker compose down
```

EF Core migrations are applied automatically on startup — no manual `dotnet ef database update` step required.

## Architecture

The entire bootstrap lives in `FlightApp/Program.cs` (minimal hosting model — no `Startup.cs`). All HTTP endpoints are versioned under `/api/v1`.

```
Request → Rate Limiter → Auth Middleware → Endpoint Group → Service → EF Core → PostgreSQL
                                                    ↓
                                             SignalR Hub (real-time)
```

**Key design decisions:**

- **Soft delete** — primary entities carry a `DeletedAt` timestamp; query filters exclude deleted records transparently.
- **Pagination** — list endpoints return `PagedResult<T>`.
- **snake_case** — database columns (EFCore.NamingConventions) and JSON enum values.
- **UUID PKs** — generated by `gen_random_uuid()` in PostgreSQL.
- **JSONB audit log** — `AuditLog` table stores before/after entity snapshots.
- **Native PG enums** — 8 enums mapped at both the data source and EF level for type safety.

## Authentication & Authorization

Authentication is delegated to **Keycloak** (realm `flightks`). The API accepts JWT Bearer tokens issued by Keycloak.

### Token Acquisition

Clients log in via `POST /api/v1/auth/login`. Keycloak returns access and refresh tokens.

### Role Policies

Three policies are defined in `FlightApp/Auth/Policies.cs`:

| Policy | Role | Access |
|--------|------|--------|
| `User` | `user` | Standard booking & profile operations |
| `Admin` | `admin` | Full platform management |
| `FlightManager` | `flight_manager` | Operational schedule and ticket management |

Roles are extracted from `realm_access.roles` in the JWT payload by `KeycloakRoleClaimsTransformer`.

### User Resolution

`ICurrentUserAccessor` / `CurrentUserAccessor` resolves the Keycloak `sub` claim to a local `User` record (synced on first login).

### Docker Networking Note

Issuer validation is intentionally disabled. Tokens arrive with issuer `localhost:8080` but the in-container JWKS endpoint is `keycloak:8080`. `KeycloakBackchannelHandler` rewrites the URI for the key fetch.

## Real-time (SignalR)

Three SignalR hubs are available over WebSocket. Auth token must be passed as the `access_token` query string parameter (standard SignalR JWT workaround for WebSocket transport).

| Hub | Path | Purpose |
|-----|------|---------|
| Seats | `/hubs/seats` | Real-time seat availability per flight schedule |
| Notifications | `/hubs/notifications` | Per-user notification push |
| Admin Dashboard | `/hubs/admin-dashboard` | Live metrics for admin dashboard |

## Rate Limiting

Rate limiting is applied globally and per-route sensitivity tier.

| Policy | Scope | Algorithm |
|--------|-------|-----------|
| Global | Per user (`sub`) or IP | Token bucket / sliding window |
| `PublicSearchPolicy` | Search & autocomplete endpoints | Higher limit |
| `SensitiveWritesPolicy` | Payment and inventory mutations | Stricter limit |

In-memory (single-instance) or **Redis-backed distributed** limiting can be toggled via configuration.

## Database

**PostgreSQL 17** with the following conventions:

- Snake_case column names (EFCore.NamingConventions)
- UUID primary keys via `gen_random_uuid()`
- Soft delete via `DeletedAt` timestamp with EF query filters
- Native PostgreSQL enum types for all status fields
- JSONB column in `AuditLog` for entity change history

### Domain Model

```
Catalog
  Airline ──► UploadedFile (logo)
  Airport (with timezone)
  Aircraft ──► Seat[]

Scheduling
  Flight (route: airline + origin + destination)
  FlightSchedule (instance: aircraft, times, status, availability)
    ├── FlightSchedulePrice[] (per-cabin pricing)
    └── FlightSeat[] (per-seat status)
  Itinerary (multi-leg) ──► ItinerarySegment[]

Booking Flow
  Booking ──► Passenger[] ──► Ticket[]
           └──► Payment ──► PaymentRefund
           └──► BookingBaggage[] (links to BaggageOption)

Platform
  Notification, UploadedFile, FeatureFlag, AdminLog, AuditLog, AiSearchDocument
```

### Adding a New Feature

The standard path for a new domain feature:

1. **Entity** — add to `Models/Entities/`, configure in `Data/DBContext.cs`
2. **Migration** — `docker compose run --rm api dotnet ef migrations add <Name>`
3. **DTOs** — add request/response records to `Models/Dtos/`
4. **Mapper** — add extension method in `Mappers/`
5. **Service** — implement interface in `Services/Interfaces/`, register scoped in `Program.cs`
6. **Endpoint group** — create `MapXxxEndpoints` extension in `Endpoints/V1/`, wire into `Program.cs` on the `/api/v1` group with `.RequireAuthorization(Policies.*)` as needed
